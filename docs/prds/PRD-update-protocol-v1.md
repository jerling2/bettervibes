# §1.0 Glossary

- **`bettervibes init`**: the existing CLI subcommand that creates the
  `bv_orchestration/` directory inside a consumer project on first use.
- **`bettervibes update`**: the new CLI subcommand introduced by this PRD;
  refreshes BV-shipped files inside a consumer project's existing
  `bv_orchestration/` without touching consumer-authored data.
- **BETTER_VIBES.md**: the customizable conventions document at
  `bv_orchestration/BETTER_VIBES.md`, copied from `BETTER_VIBES_TEMPLATE.md`
  on `init`. Consumers customize it after init.
- **BETTER_VIBES_TEMPLATE.md**: the bundled template at
  `docs/templates/BETTER_VIBES_TEMPLATE.md` in the BV repo, used as the
  source for `BETTER_VIBES.md` on first init.
- **BetterVibes** (BV): the orchestration CLI that drives a filesystem task
  queue and coordinates Claude Code workers under human review.
- **Bucket**: a directory that is part of BV's filesystem contract — its
  existence is required for runtime, but its contents are consumer-owned.
  Examples: `tasks/new/`, `tasks/stage/`, `tasks/done/`,
  `logs/worker-reports/`, `scripts/`.
- **bv_orchestration**: the BV root directory inside a consumer project;
  the marker that identifies the project to the CLI.
- **BV-owned file**: a file BV ships into a consumer project and considers
  canonical — `update` overwrites it from the bundled source on every run.
  Today: `scripts/inventory.ts`.
- **Consumer project**: any project that runs the BV CLI; identified by a
  `bv_orchestration/` directory at its root, created by `bettervibes init`.
- **Consumer data**: files and directory contents under
  `bv_orchestration/` that are authored or generated by the consumer
  project, not by BV. `update` never inspects or modifies these.
  Examples: task specs under `tasks/`, worker reports under
  `logs/worker-reports/`, `inventory.csv`, `checkpoint.sqlite`.
- **`--dry-run`**: a flag to `bettervibes update` that prints the actions
  the command would take without performing any filesystem writes.
- **Manifest**: a single source of truth, exported from `src/manifest.ts`,
  that enumerates every directory and file BV ships into a consumer
  project, tagged by `kind` (`directory`, `seeded-file`, `owned-file`).
  Both `init` and `update` iterate the manifest.
- **Project root**: the parent of `bv_orchestration/`, resolved by walking
  up from cwd or named explicitly via `--project-root`.
- **Seeded file**: a file BV writes into a consumer project once on `init`
  and then leaves alone — consumers are expected to customize it. `update`
  restores a missing seeded file from the bundled source but never
  overwrites an existing one. Today: `BETTER_VIBES.md`.

# Executive Summary

BetterVibes ships a filesystem layout into consumer projects via
`bettervibes init`: a set of buckets that hold consumer data and a small
set of bundled files. As BV evolves, the bundled files drift from what
lives in any given consumer project, and the buckets themselves can be
accidentally deleted by a botched git operation. The Update Protocol
(§2.0) introduces a `bettervibes update` subcommand that brings a
consumer project's `bv_orchestration/` back in sync with the installed BV
version, with one load-bearing guarantee: it never touches consumer data.

The protocol is built around a manifest, a single source of truth in
`src/manifest.ts` that enumerates every path BV ships, each tagged with
one of three behavioral kinds. **Directories** (buckets) are recreated
recursively if missing; their contents are never inspected. **Seeded
files** (today, `BETTER_VIBES.md`) are restored from the bundled template
if missing, but an existing copy is never overwritten — consumers
customize these. **Owned files** (today, `scripts/inventory.ts`) are
compared against the bundled source and overwritten only when they
differ. After applying the manifest, both `update` and the refactored
`init` write `bv_orchestration/.bvversion`, a single-line internal
version stamp that costs nothing today and provides a seam for future
migration logic. Files outside the manifest — `inventory.csv`,
`checkpoint.sqlite`, everything under `tasks/`, everything under
`logs/worker-reports/` — are invisible to `update` by design. `update`
prints one status line per manifest entry — `created`, `restored`,
`updated`, or `unchanged` — followed by a final version line. A
`--dry-run` flag runs the same compare logic and prefixes each action
verb with `would `, without writing.

The same PR refactors `bettervibes init` to iterate the manifest so that
"what BV ships into a consumer project" has one answer instead of two,
and adds a contributor-facing warning to BV's `.claude/CLAUDE.md`:
because `update` does not overwrite an existing `BETTER_VIBES.md`,
editing the bundled template is a breaking change for downstream
consumers and requires a major version bump plus a CHANGELOG note
instructing manual merge.

# §2.0 Update Protocol

## §2.1 **Context** | *Update Protocol*

A consumer project that has run `bettervibes init` ends up with a
`bv_orchestration/` directory that mixes two kinds of state: a small set
of files BV places (a template document, a vendored script) and a
growing body of data the consumer authors and generates (task specs,
worker reports, inventory). When BV releases a new version with bug
fixes or new bundled files, the consumer has no clean way to refresh
the BV-placed half without risking the consumer-owned half. The Update
Protocol fills that gap with a `bettervibes update` subcommand that is
narrow by construction: it only acts on paths it owns, declared in a
manifest, and it never inspects anything else.

The same manifest also becomes the source of truth for `bettervibes
init` (init refactor chosen over inline duplication — see §2.4 FR-9), so
adding a future bucket or BV-owned file is a one-line change in one
place instead of a coordinated edit across init and update. The
filesystem-shape decisions established in PRD-orchestration-v1's §6.0
Project Layout still hold; this PRD layers a refresh protocol on top of
them.

## §2.2 **Target Users** | *Update Protocol*

1. Human developer: runs `bettervibes update` from a consumer project to
   refresh BV-shipped files after a BV upgrade or to repair a
   `bv_orchestration/` directory that has lost a required path.
2. BV contributor: edits bundled assets (templates, scripts) and needs
   to know which edits propagate automatically to existing consumers
   via `update` and which require downstream manual action.

## §2.3 **User Stories** | *Update Protocol*

1. Human developer: "As the human, I want to update my consumer
   project's `bv_orchestration` files after a BV upgrade, so that I get
   the new bundled files without losing my task specs, worker reports,
   or inventory.csv."
2. Human developer: "As the human, I want a `--dry-run` option, so that
   I can see what `update` will change before it changes anything."
3. Human developer: "As the human, I want `update` to recreate any
   missing BV-owned buckets, so that runtime doesn't fail on a
   partially-deleted layout."
4. BV contributor: "As a contributor, I want one source of truth for
   what BV ships into a consumer project, so that adding a new bucket
   or file is a one-line change, not a sweep of init.ts and update.ts."

## §2.4 **Functional Requirements** | *Update Protocol*

FR-1: The BV CLI exposes a new subcommand `bettervibes update
[--project-root <path>]` alongside the existing `init` and
`inventory-sync` subcommands. `--project-root` is stripped upstream by
`extractProjectRoot` and passed to the subcommand handler as deps —
same shape as the other subcommands.

FR-2: `bettervibes update` resolves the project root via
`resolveProjectRoot` (the runtime walk-up path). If no `bv_orchestration/`
marker is found at or above the resolved target, the subcommand writes
an error to stderr and exits with code 2.

FR-2-tradeoffs:
a. Mirror of init's "refuse if already init'd" guard chosen — update
   requires an existing project, init requires no existing project;
   running either in the wrong state is a user error worth surfacing
   loudly.

FR-3: A new module `src/manifest.ts` exports a function that, given the
paths object built from a project root, returns the list of manifest
entries. Each entry carries a `kind` (`directory`, `seeded-file`, or
`owned-file`), the target path under `bv_orchestration/`, a relative
path used for printed output, and — for file kinds — the bundled
source path.

FR-3-tradeoffs:
a. Manifest in its own module chosen over inline lists in init.ts and
   update.ts — single source of truth means future additions are a
   one-line change in one place.
b. Three discriminated kinds chosen over a single uniform "file" entry —
   the kind drives update behavior, so encoding it in the data is
   cheaper than re-deriving it in update.ts.

FR-4: For each `directory` manifest entry, `update` ensures the
directory exists via recursive mkdir. Existing directories are left
untouched. The contents of these directories are never listed,
inspected, or modified by `update`.

FR-5: For each `seeded-file` manifest entry, `update` checks whether the
target exists. If it does not, `update` copies the bundled source into
place. If it does, `update` leaves it untouched.

FR-5-tradeoffs:
a. Restore-if-missing chosen over strict never-touch — a missing seeded
   file is almost always accidental (botched git, accidental delete),
   and a restored file is recoverable since the consumer can re-edit
   or re-delete.
b. Never-overwrite chosen over auto-merge — consumer projects customize
   seeded files (notably `BETTER_VIBES.md`), and auto-merging against a
   deliberately diverged file creates more friction than value.

FR-6: For each `owned-file` manifest entry, `update` compares the
bundled source to the existing target. If they differ, `update`
overwrites the target with the bundled source. If they are identical,
`update` performs no write.

FR-6-tradeoffs:
a. Compare-then-write chosen over unconditional overwrite — the
   on-disk result is identical, but the compare enables meaningful
   per-entry output (see FR-7) and avoids unnecessary mtime churn on
   identical files.

FR-7: For each manifest entry, `update` writes exactly one status line
to stdout, in manifest order. The verb names the action taken:
`created:` for a newly-created directory, `restored:` for a
newly-copied seeded file, `updated:` for an overwritten owned file,
and `unchanged:` for any entry whose target was already in the desired
state. After all entries are processed, `update` writes a final
version line: `version: <X>` when BV's current version matches the
version recorded in `.bvversion`, or `version: <X> -> <Y>` on any
mismatch (where `<X>` is `(none)` if no `.bvversion` existed at the
start of the run).

FR-7-tradeoffs:
a. Always-print chosen over print-only-on-change — a stack of
   `unchanged:` lines is an "all clear" signal that builds user trust,
   where silence creates uncertainty.
b. Manifest order chosen over group-by-kind — single predictable rule;
   group-by-kind would require an additional ordering decision between
   kinds.

FR-8: After applying the manifest, `update` and the refactored `init`
both write `bv_orchestration/.bvversion` as a single line of plain text
containing the BV `package.json` version at write time. The file is
BV-internal; consumer projects do not edit it. `update` always
overwrites `.bvversion`.

FR-8-tradeoffs:
a. Version file added in v1 chosen over deferring entirely — it does
   nothing today, but provides a seam for future migration logic to
   answer "what version produced this consumer's `bv_orchestration/`
   state?" without resorting to heuristics. If migrations never
   materialize, the cost is one file containing one line.
b. Plain text chosen over JSON — minimal format; a future migration
   can rewrite the file to richer state because it is BV-internal and
   has no external readers to break.
c. Outside the manifest chosen over a fourth `kind` — a single-instance
   generated file does not justify a generalized "generated" kind. If
   more generated files appear, the manifest can grow a kind then.

FR-9: `bettervibes update --dry-run` performs no filesystem writes. It
runs the same compare logic as a real `update` and prints the same
status lines, but the action verbs are prefixed with `would `:
`would create:`, `would restore:`, `would update:`. `unchanged:` lines
are printed as-is. The version line in dry-run becomes
`would write version: <X>` (or `would write version: <X> -> <Y>` on
mismatch). `update --dry-run` exits 0.

FR-9-tradeoffs:
a. `--dry-run` chosen as a v1 feature rather than a deferred follow-up
   — `update`'s contract is "don't lose my data," and `--dry-run` is
   the cheapest way to let a cautious consumer verify the planned
   actions before committing.

FR-10: `update` does not detect, list, or remove files that exist
under `bv_orchestration/` but are not present in the manifest. Orphan
cleanup is left to the consumer and documented in the CHANGELOG when
a BV-owned file is dropped from a future BV version.

FR-10-tradeoffs:
a. No auto-cleanup chosen over automatic removal — auto-deletion of
   files not currently in the manifest risks destroying consumer data
   if the manifest is misclassified; the safer default is to leave
   stale files and require manual cleanup.

FR-11: `bettervibes init` is refactored to iterate the same manifest.
For each `directory` entry, init recursive-mkdirs the path. For each
`seeded-file` entry, init copies bundled → target (on a fresh init the
file does not exist, so the restore-if-missing rule trivially holds).
For each `owned-file` entry, init copies bundled → target. After the
manifest is applied, init writes `.bvversion` (FR-8). Init's existing
pre-condition (refuse if already init'd) and post-condition of
printing the "add to .gitignore" line are unchanged.

FR-11-tradeoffs:
a. Init-via-manifest chosen over keeping init's inline lists separate
   — duplication grows as BV ships more files; centralizing keeps
   "what BV ships" and "what update updates" identical by construction.
b. Refactor in the same PR chosen over a follow-up PR — landing both
   at once keeps the manifest's single-source-of-truth claim true from
   the first commit.

FR-12: BV's `.claude/CLAUDE.md` carries a contributor-facing warning:
because `update` does not overwrite an existing
`bv_orchestration/BETTER_VIBES.md`, any edit to
`docs/templates/BETTER_VIBES_TEMPLATE.md` is a breaking change for
existing consumers and requires a major version bump plus a CHANGELOG
note instructing them to diff the template and manually merge.

FR-12-tradeoffs:
a. `.claude/CLAUDE.md` chosen as the durable home for the warning —
   the file is loaded into context for any Claude Code session in the
   BV repo, so a contributor working on the template will see the
   constraint before changes ship.

## §2.5 **Non-Functional Requirements** | *Update Protocol*

NFR-1: `bettervibes update` exits with code 0 on success (whether or not
any files changed) and code 2 on fatal error (no project root resolved,
I/O failure). This matches the convention established by `init` and
`inventory-sync`.

## §2.7 **Mock Flow** | *Update Protocol*

Flow A: *standard update on a healthy consumer project*
1. Alice runs `bettervibes update` inside a consumer project (FR-1).
2. The CLI strips `--project-root` if present and dispatches to the
   `update` subcommand handler.
3. `update` resolves the project root via `resolveProjectRoot` (FR-2).
4. `update` builds the paths object from the resolved root, then loads
   the manifest (FR-3).
5. For each manifest entry, `update` applies the rule for its `kind`:
   recursive mkdir for `directory` (FR-4), copy-if-missing for
   `seeded-file` (FR-5), compare-then-copy for `owned-file` (FR-6).
   `update` writes one status line per entry to stdout (FR-7).
6. After the manifest is applied, `update` writes
   `bv_orchestration/.bvversion` and prints the corresponding version
   line (FR-7, FR-8).
7. `update` exits 0 (NFR-1).

Flow B: *dry-run*
1. Alice runs `bettervibes update --dry-run` inside a consumer project.
2. Steps 2–4 of Flow A run identically.
3. For each manifest entry, `update` runs the compare logic and prints
   the status line it would write — `would create:`, `would restore:`,
   `would update:`, or `unchanged:` — without performing any write
   (FR-9). The version line is printed as `would write version: <X>`
   (or `would write version: <X> -> <Y>` on mismatch).
4. `update --dry-run` exits 0.

Flow C: *missing seeded file restored*
1. A consumer project has `bv_orchestration/` but `BETTER_VIBES.md` was
   accidentally deleted.
2. Alice runs `bettervibes update`.
3. `update` iterates the manifest. For the `seeded-file` entry
   `BETTER_VIBES.md`, it observes the target is missing and copies the
   bundled template into place (FR-5).
4. Alice re-runs `update`; the file is present and `update` leaves it
   untouched (FR-5).

Flow D: *not init'd*
1. Alice runs `bettervibes update` in a directory that has no
   `bv_orchestration/` marker at or above it.
2. `resolveProjectRoot` throws.
3. `update` writes an error to stderr and exits 2 (FR-2, NFR-1).

## §2.8 **Cross-Cutting Tradeoffs** | *Update Protocol*

a. (Future-proofing) BV-owned-vs-consumer-data is a property of the
   manifest, not of any particular file's location. A future BV version
   can add new buckets, new owned files, or new seeded files without
   redesigning the update flow — only the manifest grows.
b. (Other) `update` is conservative by design: it ensures missing-but-
   needed paths exist and refreshes BV-owned code, but it never deletes,
   modifies, or inspects consumer data. The conservatism is deliberate;
   the consumer's stated motivation is "don't lose my data."
c. (Cost) Migration scripts and schema versioning are deferred. Worker
   report and task spec schemas have been stable since v1.0.0; building
   a migration framework before there is a migration to write would be
   speculative scaffolding. The `.bvversion` seam (§2.6 Q3) is the
   smallest hedge against that future.

# Appendix A: Narrative

I read `init.ts`, `paths.ts`, and the bundled assets to map what BV
currently writes into a consumer project. I classified those writes into
three groups by update-time behavior: directories that need to exist but
whose contents are consumer-owned; seeded files that BV provides once
but the consumer customizes; and owned files that BV holds canonical and
should be refreshed on every update. Joseph's prompt anchored the design
at "don't lose my data" — worker reports, task specs, and inventory.csv.
The classification followed from that constraint: any path whose
contents are consumer-authored must be invisible to `update`.

The design surfaced in pieces. I sketched the argv shape and project-
root resolution, then the manifest, then queued per-file diff behavior,
the `.bvversion` seam, output shape, and exit codes for later. Joseph
pushed back on the manifest as files-only and insisted directories
belong in it too — the buckets themselves are part of BV's contract, and
a missing `tasks/new/` breaks runtime before any file is read. That
correction reshaped the manifest from a flat list of `(bundled, target)`
pairs into a discriminated list with three kinds.

Joseph approved restore-if-missing for seeded files, with the strict
constraint that an existing seeded file is never overwritten. He
flagged a downstream consequence: when BV updates
`BETTER_VIBES_TEMPLATE.md` upstream, existing consumers will not pick up
the new template via `update` — that requires a manual diff and merge.
He asked for a contributor-facing warning to be recorded in BV's
`.claude/CLAUDE.md` because the constraint is important.

He approved no auto-cleanup for orphan files in v1 (changelog handles
that), approved `--dry-run` for v1, and asked what the init refactor
was. I described it as routing init's directory creations and bundled
copies through the manifest so init and update share the same source of
truth about what BV ships; he approved doing the refactor in the same
PR.

Joseph asked to resolve the open questions before implementation began.
I drafted positions on all four — compare-and-report behavior for owned
files (Q1), `.claude/CLAUDE.md` as the only home for the contributor
warning since the bundled template is copied verbatim to consumer
projects on init (Q2, a reversal of the "both" position I had taken in
the prior turn), the `.bvversion` seam written by both init and update
(Q3), and an always-print-every-entry output shape in manifest order
(Q4). Joseph approved each. The resolutions migrated into the FRs above:
FR-6 became compare-then-write, FR-7 codified the output verbs and
ordering, FR-8 introduced `.bvversion`, FR-9 (dry-run) inherited the
same verbs prefixed with `would `, and FR-11 (init refactor) extended
to write `.bvversion` alongside the manifest. §2.6 is empty at the
time of writing.
